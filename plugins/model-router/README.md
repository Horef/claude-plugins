# model-router

Routes each step of a multi-step task to the cheapest model tier that does it well, shows what it cost and what it saved, and learns from your reruns.

## Start here

1. Install: `/plugin install model-router --marketplace Horef/claude-plugins`, then type `/reload-plugins` in chats that are already open (new chats load it by themselves).
2. Ask for something with several steps, e.g. "In three steps: find the five largest files here, summarize each, and pick the one most worth cleaning up". A single-step request is not planned; that is intended.
3. Approve the plan in the question that appears: each step then runs on the cheapest model that does it well.
4. `/router` opens the pane: the steps, the models they ran on, the cost and what it saved. `/router help` is a one-minute tour in the chat.
5. `Router on · helpers off` is normal: Claude subagents work with no extra setup; helpers (other subscriptions) are optional and come later.
6. The guide, with pictures: https://horef.github.io/claude-plugins/model-router.html
7. Updates: a plugin does not update by itself. The pane shows `↑ model-router x.y.z available` when a newer version exists, and `/router update` puts the request that updates it in your prompt box. How it works: https://horef.github.io/claude-plugins/updating.html

## How it works

- **Plan**: for a multi-step request the main agent first calls `mcp__model-router__plan` with steps tagged by tier (light, standard, deep) and by where they run (a subagent, or here in the main chat).
- **Parts**: a step may have `parts`, recursively (a part's id extends its parent's: `s3`, `s3.a`, `s3.a.1`), for work that splits into pieces that need different tiers or run side by side. A step with parts is a **group**: its tier only rates it, it is done when all its parts are, and its cost and usage are the sums of its parts. A part with `count: N` is N identical agents running in parallel under one id (N readers, say); it is done when the Nth run ends, and its agents' costs add up. Each part is delegated under its own id (`[s3.a.1]`); delegating the group itself is refused with the list of its parts. Naming a group in `done` marks its unfinished parts done; naming it in `start` starts them. A plan nested deeper than three levels of parts is still taken (the tool's schema spells out three). A repeated id is ignored and the agent is told.
- **Approval**: the plan waits for your answer in the chat's question dialog. Edits you make in the pane while it waits (tier, where, model, thinking) are kept whatever you pick.
  - **Run it**: go with the plan as it now stands in the pane.
  - **Run it, and auto-approve future plans**: the same, and later plans run without asking.
  - **Change the steps**: the steps themselves need work (add, drop, split or reword). Nothing runs; the model asks what to change, or, if you typed it under Other, revises right away and asks again.
- **Routing**: an Agent call whose description starts with `[<step id>]` gets its model and thinking level from the plan, whatever the main agent asked for. The Agent call itself goes through unchanged, so auto mode's review of it stands: the model (and the scope note) are set as the subagent starts, its thinking level on each of its requests. Forks are never rerouted, since they always inherit the parent model. The rung comes from, in order: your own picks on the step in the pane, auto mode's learned rung for the step's kind (when auto mode is on), the kind's default (set by applying advice), the tier.
- **Kinds**: each step may carry a `kind`, a short label for the kind of work (`code-review`, `summarize`, `search`, `write-code`, `figure`). The rules list the kinds the history has seen so far (taken when the chat starts, so the rules stay the same all chat), and the agent reuses them. A step routed for a mapped skill takes the skill's name as its kind. Kinds are stored as lower-case letters, digits and hyphens.
- **Verdicts**: every delegated step (subagent or helper, parts included) gets a verdict from the main agent once it has checked the result: `done: [{id, verdict, why}]`. The verdicts are defined by what happened, not by taste: **ok** = the result was used as returned or with small edits; **weak** = it needed a rerun, the agent redid part of it, or review found a substantive error; **overkill** = plainly mechanical work (finding, listing, extracting, short output, no judgment) that ran above the light tier; **cut-short** = the run was stopped by something outside the model (lost connection, quota or rate limit, a crash, you stopping it), so it says nothing about the model. A subagent step is marked done when its agent ends; the agent still gives it a verdict. A delegated step marked done without one is still done, the plan tool's result asks for it in one line (once, or again when the step is named again) and so does the router note at the start of the next turn (once per step: after a plan's last step the plan tool is usually not called again), and the run counts as "no verdict".
- **Facts per run**, recorded without asking: kind, tier, where, the rung it ran on (model and thinking level, or the helper template), reruns, output tokens, start-up heavy, and how long it took. A finished step delegated again counts as a rerun, as does a rerun from the pane; the advice counts a rerun as weak whatever the verdict said.
- **Cut short**: a run marked cut-short (by the agent, or with the quiet *cut short?* link on a finished delegated step's card; *undo* puts the earlier verdict back, in the plan and in the history) is left out of everything that judges rungs: the advice, auto mode's learned rungs, and the helpers' advice and picks. The stats tables count such runs apart ("2 cut short"). A step delegated again after its last run was cut short is not a rerun (no rerun flag, no rerun count), from the pane too.
- **Always plan** (Settings): every message you type carries a hidden reminder to plan before using tools.

## The pane (`/router`)

One layout on every surface (desktop app, VS Code, terminal, mobile), top to bottom: health line, new-models card (only when something is pending), plan, cost, footer. Detail is one click away (▸, `?`, *Details ▸*), never on the first screen.

- **Health line**: always first. Quiet when all is well: `✓ Router on · helpers: Herdr (Kiro, Copilot, Antigravity)`, `✓ Router on · helpers: direct mode (no Herdr terminal)`, or `Router on · helpers off`. When other subscriptions are on but cannot run it names the first failing check, `✗ Helpers can't run: this chat is not inside a Herdr terminal`, with *Why ▸*: the full list of checks (switched on · herdr-delegate's helpers.py found · Python runs it · a helper CLI installed · hc found · inside a Herdr terminal · direct mode available · helper rules delivered to this chat), each failure with a one-line fix, the checks after a failed prerequisite skipped, and *Write report*. The status line adds ` · helpers ✗` in that state.
- **Update notice**: when a newer release is known and not dismissed, one quiet line directly under the health line: `↑ model-router 0.30.1 available`, then *What's new ↗* (the CHANGELOG), *Update* (puts the update request in your prompt box; press Enter and Claude runs `claude plugin marketplace update` and `claude plugin update` with its shell, which also works in the desktop app; when the box cannot take it the pane shows the text), *How ↗* (updating.html) and *×* (dismiss this version; a later one shows again). See Update check below.
- **Plan**: a header `Plan · 2 of 5 done` (`· awaiting your approval` while the plan waits for you, with one line on what to do), a `?` glossary (light · standard · deep, this chat · Claude agent · other subscription, kind, verdict, effort, saved, and in the terminal ⇄ and ▾: one line each, a term and its meaning under it in the terminal) and *Expand all* / *Collapse all*. With no plan: `No plan yet. Multi-step tasks show their steps here.` (and how to plan every message, while that is off). On a fresh start (no plan, no history, no plan ever posted, and not dismissed) that line is replaced by a welcome: `New here? Three steps:` with the starter request, *Guide ↗* and *Got it*; *Got it*, or the first plan posted, ends it for good (stored as `welcomeSeen` in the store), and anyone with history never sees it.
  - **A step is a row of two lines**: ▸, status, id (never broken) and the title, which alone wraps; then the pickers for where it runs (*this chat*, *Claude agent*, or *other subscription* when those are on; `other sub` in a narrow terminal), its level, and a Claude agent step's model and effort, its kind (and `×N` for a counted step), its cost, the verdict word, short warnings (`⚠ rated for opus`, `⚠ start-up heavy`) and *↑ Rerun on …*. A finished step shows quiet text instead of pickers (`Claude agent · standard · sonnet high`), since changing it would do nothing. A group's line 2 is `rated deep · 2/3 done · ≈$x`.
  - **▸ opens the step's details in place**: tokens and saving, where its rung comes from ("auto: sonnet · high (learned, 5 runs)", "code-review default: sonnet · medium"), the helper launch line or why none could be made, the helper's usage and time, the fallback reason, the verdict's why with the quiet *cut short?* link, and the full warnings. *Expand all* opens every step; it is remembered as the default for new chats (as the old Minimal view switch was: stored settings from 0.25 with the full view open every step, Minimal and new installs start closed). Steps opened one by one reset with a new plan.
  - **Groups and parts**: parts sit under their group, indented two cells a level (the indent stops at three levels). A group is a row with its rating, `n/m done` and the cost of its parts; every part is a row of its own with its own pickers, rerun and cost, and a `×N` tag (with the runs finished so far) when it has a count. Only the parts that do the work count as steps in the header and the status line.
  - **Steps done in this chat** run on this chat's own model and effort, which no level can change: the level is a rating ("rated deep") that becomes a picker again when you send the step to a Claude agent, and a step rated above this chat's model (a deep step in a Sonnet chat) is flagged on its row and in the plan the agent gets back.
- **Edits after approval**: change a part's (or step's) where, level, model or effort in the pane while the plan runs and the change goes to a draft, not to the plan: the routing and the main agent keep using the plan as it was, so a half-finished edit cannot reach the agent if a turn starts meanwhile. The edited values carry a ✎ mark, and the top of the plan shows **Send changes (N)** (N counts the changed values) and **Discard**. Send puts the draft into the plan at once (a step not yet started is routed by it from then on) and the main agent is told at its next turn, as one router note per step or part with the final values (so cycling a picker through several values sends one note, and none if you put it back); until then the row says "change noted, applies from the next turn". Discard drops the draft. A picker put back to the plan's own value leaves no edit. A plan posted anew drops an unsent draft; a rerun drops the unsent model and effort picks of its step. Before the plan is approved (while it waits for you) edits go straight into the plan, since approval sends them. A rerun needs no note: its own message carries the new rung.
- **Rerun one rung up**: a finished step that came back weak can be redone on the next rung of the ladder (Haiku low → medium → high → Sonnet medium → high → Opus high → xhigh → Fable). The main agent is asked to delegate it again. With more models known, the ladder is built from them ordered by price: each default model keeps its rungs, a new one gets medium and high, and a model with no price is not on it.
- **Cost**: one line, `This plan ⇄ this chat ≈$x · Claude agents ≈$y · saved ≈$z (n%)`; the button cycles the span:
  - **This plan**: the main chat since the plan was posted, its subagents, and what they saved. A new plan (no step in common with the last) starts a new count.
  - **This chat**: since the chat was opened or its plugins reloaded; earlier turns are not counted.
  - **All time**: since the first use or the last reset, remembered across chats as a handful of numbers.
  Under it the *Moved off Claude* line (with other subscriptions on, see below) and the history in one line (`History: no runs yet; advice starts after 3 runs of a kind.`, `History: 12 runs; advice needs 3 on one rung.`). *Details ▸* opens the span's tiles (main chat, subagents, saved as a share of what the same work would have cost without routing; all time: saved, what the subagents cost and what they would have cost on the main model), its footnote (steps and plans by level), and the history tables: runs, reruns, average cost and verdicts per rung, and per kind. Every view moves together: cost is counted per model response as it arrives, not when a step finishes. All amounts are estimates from list prices (`hooks/tiers.ts`, editable in Settings → Models and prices) and the token counts the API reports; savings compare each step with the main chat's model doing the same tokens. Tokens on a model with no price show their cost as "?" (or "≈$0.12 + ?" when only part is unpriced) and are left out of savings.
  - **Advice** stays visible under the cost, one line each with *Apply*: per kind, and per level for runs with no kind, once there are at least 3 runs on the rung it runs on now: one rung up when at least half were weak (a weak verdict or a rerun), one rung down when at least half were overkill and none of the last 3 was weak. Each shows its evidence ("code-review on light: 3 of 4 weak"). For a kind it sets the kind's default (Settings → Learning), for a level that level's model and effort. Only Claude agent runs move a Claude agent rung; helper runs have advice of their own (see Helpers, below). A plan with no deep step in an Opus or Fable chat adds one line suggesting Sonnet for the chat itself.
- **Genome link**: when a kind's advice first reaches its threshold, and only on a machine with a strange-loop genome (the file `${XDG_CONFIG_HOME:-~/.config}/strange-loop/genome`), the router queues one note asking the main agent to record a strange-loop observation with the note command and the evidence line (to the skill of that name if the kind is a skill, else to model-router), once per kind and direction, remembered across chats.
- **Footer**: *Settings ▸*, *Guide ↗* (the web guide) and *Write report* (with where it went beside it). *Clear plan* sits at the end of the plan.
- **Settings** take the place of plan, cost and footer until *Done* (at the top); the health line and the new-models card stay. In the terminal a setting's name is bold with its control on the same line and its one-line why dim under it. A small • marks every value that differs from the default (one-line legend), and the closed header of a group with such a value inside.
  - **Basics**, always shown, each with one line on what it changes: *Ask me before a plan runs* (the inverse of auto-approve), *Plan every message* (always plan), *Other subscriptions* (Off / Long steps / All steps; when on and something fails, `✗` and the first failing check; the health line already says when it is ready), *Spend* (Thrifty: haiku low, sonnet low, opus medium · Balanced, the shipped default: haiku low, sonnet medium, opus high · Best quality: haiku high, sonnet high, opus high · Custom, shown whenever the levels match no preset; picking Custom opens Models per level), *Open the pane in new chats*.
  - **Groups**, one line each while closed, a summary of what is inside (hidden while open, unless something fails); which are open is remembered (`openGroups`). A value typed into an input that is not taken (a path, a price, a model name) says why under the input:
    - **Models per level** (`light Haiku low · standard Sonnet medium · deep Opus high`): each level's model and effort for steps run by a Claude agent, with what the level is for. The model pickers list every known model.
    - **Other subscriptions** (`Kiro, Copilot, Antigravity · Herdr`, or `✗ <failing check>`): the failing helper checks with their fixes, a pending one on its own quiet line (`– Helper rules go to the chat with your next message`), and the rest as one count (`✓ 5 checks pass · 1 not needed`, or `· 3 skipped` after a failure; *Show* lists them), *Run helpers*, *Copilot Fusion*, the **Order** (one line a level, `deep: kiro → copilot → agy`, with *Edit* for that level's ↑ ↓ off / + name controls, one level at a time, and *Reset to default order* once an order was changed), **Helper models** (only the levels that differ from herdr-delegate's defaults, one line a provider, `Kiro: standard claude-opus-5.5 high · deep … •`; another Claude account is compared with herdr-delegate's defaults for Claude accounts; *Change…* opens every provider's model and effort pickers; *Check models*), per-kind helper choices with *reset*, and helpers.py's path under *Set path by hand*. While off, one line on what it does.
    - **Learning** (`auto off · 2 kinds tuned`): *Auto mode* (off by default): a Claude agent step whose kind has enough history runs on the learned best rung, the cheapest rung with ok or overkill (and no rerun) in at least P% of at least N runs there (overkill means the rung was more than enough, so it counts as passing; the advice still weighs it), 5 runs and 90% by default (a mode that changes routing without asking wants more evidence than the advice does); else the kind's default; else the level's. A run with no verdict (and no rerun) is left out of that share: the lead did not judge it, so it says nothing either way (a rerun still counts as weak). *Try a cheaper rung now and then* (`autoExplore`, off by default): auto mode alone only chooses among rungs that have history, so a kind that always ran on Sonnet never learns that Haiku would do; with this on, after 4 runs on a kind's learned rung (since the last try) the next run of that kind goes one rung down the ladder. The try is pinned on the step (its card says `auto: trying haiku · high, one rung below what it learned`, the log `route` source `explore`), only one step of a kind tries at a time, a step run as N agents never tries, a weak try (or a rerun) stops the tries on that rung, so do 2N tries without N verdicts, and once the rung below has its N runs at P% ok it is the cheapest good rung, so auto mode takes it and the tries move one rung further down. A try that is run again goes back to the learned rung, and changing its model, effort or place in the pane ends it. What the agent is told, the pane's comparisons and the model map keep the learned rung; a step not yet started shows `auto: next run tries …` when the next run would try. Your own picks on a step still win. "Auto picks a rung with at least N runs and P% ok" sets the two numbers (3, 5, 8, 10 or 20 runs; 70, 80, 90, 95 or 100%). The advice's own thresholds (3 runs, half weak or overkill) are fixed. Below that, each kind's default (set by Apply) with *reset*. With other subscriptions on, auto mode and its two numbers also pick a helper's model (see Helpers).
    - **Models and prices** (`5 models · 1 without price · 12 notes`): the known models are the defaults, any model id seen in a chat's usage (ids map to family aliases, `claude-haiku-5-5` is haiku; an unknown family is kept under its id), and any added by name. Each shows its price, which you can set: "input output" in dollars per million tokens (cache write 1.25×, cache read 0.1× input) or all four; empty brings back the default (or none). Added and seen models can be removed. A new model is passed to the Agent tool by the name the router knows it by, so add it under the alias the Agent tool takes. Then the model notes (*Check now*, *List ▸*; see New models).
    - **Skills** (`none mapped` / `2 mapped`): skills that should run as a Claude agent on a level. A skill you've used shows up here; you can also add one by name.
    - **Diagnostics** (`log on · Herdr view on`): *Keep a log* (on by default), *Write report* (see Log and report) and *Show in Herdr* (see Herdr view) and *Check for updates* (on by default; see Update check).
    - **Advanced** (`experiment off · scope notes off`): the experiment on the effort of steps done in this chat (see below), the per-level scope notes (one line added to that level's briefs: stay on the task, don't start sessions or load extra tools; off by default), and three resets. Each reset asks once, naming what goes: *Clear history (214 runs)* → `Really clear 214 runs?` *Clear* / *Keep*; *Reset statistics* (the all-time numbers); *Reset models per level* (back to Balanced, scope notes off). The result shows in place.
  - Settings opened from a fresh install: 5 Basics and 7 closed group headers (12 controls, plus *Done*).

All settings and the history are remembered across chats, in the mod's store. Settings (kind defaults, auto mode, known models and prices included), auto-approve and always-plan are also mirrored to `~/.config/model-router/settings.json` on every change: when the store is new and empty (re-adding the marketplace creates one), they come back from that file; when the store has settings, it wins and rewrites the file. History and the all-time numbers live only in the store, and nothing is written to the store until it has been read, so a response arriving while a chat loads cannot overwrite them with zeros.

Several chats can be open at once, each with its own copy of the settings read when it started. A settings change is therefore applied to what the store holds at that moment (not to the chat's copy) and written back, so a chat that started earlier never puts its older settings over newer ones; auto-approve and always-plan are single values and the mirror file follows the store. A chat re-reads settings, auto-approve and always-plan from the store at the start of each turn and when you open Settings in the pane, so a change made in another chat shows up there. Reading never writes.

**In the terminal** the pane scrolls with the keyboard: ctrl+x tab (or a click) gives it the keys, ↑↓ scroll, Esc returns to the prompt; the mouse wheel works where the terminal passes it through. A line under the health line says so. **On a short terminal** (under 50 rows: a phone, a small split) where the pane sits above the prompt, it is a glance of a few lines (the plan's progress and the step at work, or "Router on · no plan yet") until it is focused, so the status band above the prompt keeps its rows; *Show all ▾* (a tap or click) or ctrl+x tab shows the whole pane; *Show less ▴* or Esc returns to the glance. Claude Code keeps an inline pane at about a third of the screen whatever it asks for (and has no full-screen overlay for it), so after Show all the pane is paged: a fixed top row holds *Show less ▴*, *▲ Up*, *▼ Down* and the block number, and the pane below starts at one block (the top, the plan's head, each step, the cost, the footer). The mouse wheel, or a swipe the phone app sends as one, scrolls it too. The order of the sections is the same as elsewhere, also while a plan awaits approval. A picker with up to three options is a button that cycles (⇄: Enter picks the next one); a longer one (models, efforts, Spend) is a button marked ▾ that lists its options under its row, the current one marked ●, with the keyboard ring on it: ↑↓ or Tab move along the list, Enter picks and closes it, and Enter on the picker again closes it unchanged. The glossary gives each term its own line there. (The terminal's own Select is not used: only a pick closes it.)

## Helpers (other subscriptions and accounts)

Off by default; while off, nothing helper-related in the rules, the plan tool or the pane changes. When on, a plan step can run in a third place, **helper**: an agent on another subscription (Kiro, Copilot, Codex, agy) or under another Claude account (a second `CLAUDE_CONFIG_DIR`, e.g. a university plan) that the main chat starts through a delegation skill. Which providers exist, in which order, with which labels and usage units, is herdr-delegate's configuration (`helpers.py config`); the router reads it.

- **Needs** (only for helper steps; model-router works fully without them, running every step as a Claude subagent): the **herdr-delegate** plugin from the same marketplace (`/plugin install herdr-delegate@<marketplace>`), Herdr's **`hc`** on your PATH with Claude started from a Herdr terminal (or, without Herdr, direct mode: herdr-delegate 0.15 or later), and at least one helper CLI (Kiro, Copilot, Codex, Antigravity, or another Claude account). Helpers come only from what is installed: with `helpers.py` not found, or neither Herdr nor direct mode usable, or no helper CLI installed, there are no helpers at all (no default orders, no Copilot Fusion), the plan tool does not offer `where: "helper"`, the rules do not mention helpers, and a helper step in a plan is a subagent step. The mod runs no shell commands of its own while Helpers are off. While they are on it runs `hc --version` once (to see that `hc` can start), reads `$HC_TERMINAL_ID`, and runs herdr-delegate's `helpers.py` (python3, no shell) to read the config and change helper models; with the log on, it also runs `rm` on its own log files older than 14 days. The pane then explains in a few lines what to install (the install line names the marketplace this plugin came from, `horef-claude-plugins` when that cannot be read), hides the orders and pickers, and keeps the path box behind a small "Set path by hand" link; *Look again* reads everything again.
- **Run helpers** (Settings → Other subscriptions, `helpers.run`): *Herdr, else direct* (`auto`, the default) runs helpers through Herdr when hc starts and this chat runs in a Herdr terminal (`$HC_TERMINAL_ID` set), else directly; *Herdr only* never runs them directly; *direct only* always does, when it can. The mode is worked out when helpers are read (chat start, switching on, *Look again*) and when this setting changes. With no mode (outside Herdr and no direct helper, say) helpers count as not available: the plan tool offers no `helper`, the rules leave helpers out, and the health line says why, instead of offering helpers that then fail.
- **Direct mode** (needs herdr-delegate 0.15 or later, whose config marks providers with a headless command and an installed CLI `direct: true`): the rules tell the lead to pick the template with `helpers.py pick <order>`, write the brief to a file inside the workspace (keeping the helper to reading and editing files there, since nobody can approve its commands mid-run), and run `python3 <helpers.py> run <template> --brief <file> --cwd <dir>` with Bash in the background; it is notified when the run ends, reads the report file named by `out` in the JSON on the last stdout line, and passes that JSON's `usage` as is when it marks the step done. In Herdr mode rule 6 is as before.
- **Turn it on**: Settings → Basics → *Other subscriptions*: *Long steps* or *All steps*. The plan tool offers `helper` from then on: switching registers the tool again, which replaces its schema at once (and costs the chat one prompt-cache refresh).
- **Use for** (the same picker): *Long steps* sends only long self-contained steps (research, code to a spec, sweeps, over ~15 tool calls) to helpers and leaves shorter ones to subagents; *All steps* sends every self-contained step that would otherwise be a subagent step.
- **Order**: each tier lists the helpers to try, e.g. deep: `kiro-deep → copilot-deep → codex-deep`. The default order is built from helpers.py's config: the providers sorted by their `order`, that have the tier and an installed CLI (`cli_found`), and are not this session's own account (`self`); when no config is known (no `helpers.py`, no `hc`, or a config that failed) the list is empty; the old fixed string `kiro → copilot → agy` stays in the settings only as the marker for "never changed" and is never shown as helpers. An order you change is stored and wins while helpers are available; one that still equals the old default string counts as not set. A stored order that names this session's own Claude account shows it as "(this account)" in the pane and on step cards, and helpers.py's `pick` skips it. The plan and the step details show the order. Settings → Other subscriptions → Order shows each level's order on one line; its *Edit* lists that level's helpers in order with ↑ / ↓ to move one and *off* to drop it (dropped helpers, and configured providers with no installed CLI, come back with *+ name*), and *Reset to default order*. The order is stored as the comma string under `helpers.tiers.<tier>`. A changed order reaches a chat that already has the rules as one router note with the full helper rule (none if it is back to what the chat was told). When the config lists providers and none has its CLI installed, Settings says so and the rules leave helpers out, as when `helpers.py` or `hc` is missing.
- **Copilot Fusion** (Settings, off by default): *Max for deep* adds `copilot-fusion-max` to the deep order; *High + Max* also adds `copilot-fusion-high` to standard. Each goes just before the pinned Copilot helper, since both use Copilot's quota. Fusion is GitHub's router across Claude and GPT-6 models, not a fixed model. Fusion Max scored close to Claude Code with Opus 5.5 at max effort for about half the cost (measured 2026-11-01); High has not been measured (herdr-delegate's SKILL.md has the details). Changing it mid-chat sends the new orders to the chat as a router note.
- **Without helpers**: when none can run (no `helpers.py`, no CLI, or neither Herdr nor direct mode), the plan tool and the rules do not offer helper steps at all. When the rules were already in the chat and no helper is usable, the main chat first calls the plan tool with `start: [{id, fallback: "<short reason>"}]` ("no Herdr terminal", "picker found nothing", "out of quota"), then runs the step as a normal subagent and says so. The step becomes a subagent step, routed and costed like any other; its card says `ran as a subagent: <reason>`, and an Agent call that takes over a helper step without that call records `no reason given`. Fallbacks are counted per span (plan, chat, all time) with the latest reason.
- **What the chat knows of helpers** stays current: when helpers go on or off, the mode changes, "Use helpers for", Copilot Fusion or an order changes after the rules were delivered, the next turn carries one router note with the whole current helper rule ("Helpers changed; this replaces rule 6: …"), or "Helpers are now off: run every step as a subagent or here". No note when it is back to what the chat was told.
- Helper steps have no Claude subagent usage, so they show no cost and are not counted in the subagent totals. The main chat marks them done itself.
- **Which helper, which model**: when the main chat starts a helper step it calls the plan tool with `start: [{id, helper: "copilot-standard", model: "Claude Sonnet 5.5"}]` (plain ids still work): the template it launched and the model the helper reports on its own screen. The card shows "copilot-standard · Claude Sonnet 5.5 · high": the last part is the helper's thinking level. It is the `effort` the main chat reports in the same `start` object when the helper's screen shows one; else the router reads it from the helper's template, `<template>.md` (its `command:` line, under `${XDG_CONFIG_HOME:-~/.config}/herdr-core/templates/`: Kiro and Claude `--effort X`, Copilot `--reasoning-effort X`, Codex `-c model_reasoning_effort=X`, agy the level its model id ends with, e.g. `gemini-4-argon-high`); a template that sets none (Copilot Fusion chooses per step) shows no level. A later `start` that names only a model keeps the level. The router does not check the model against the template's name; it shows what was reported. On a closed part's row the same line shows for a helper part, and a Claude agent part shows its model and effort pickers.
- **Helper usage**: when it marks the step done the main chat passes its verdict and the usage `helpers.py usage <name>` (herdr-delegate) printed before it closed the helper: `done: [{id, verdict, why, usage: {provider: "copilot", amount: 30.04, unit: "AIC"}}]`. The script prints that JSON or nothing; the rules tell the lead to leave usage out when it printed nothing, never to send 0 or a guess, and an amount of 0 is ignored anyway (it would read as "used nothing"). It is recorded once per step; the card shows it with how long the step ran (from start to done), and nothing is converted to money. Plain ids still work.
- **What moved off Claude**: the cost card (plan, chat and all-time views) adds a line such as `Moved off Claude: 4 helper steps, 38 min; Copilot 30.04 AIC; Kiro 2.1 credits`: finished helper steps, their running time, and the usage added up per provider and unit. Provider names come from the config's `label`, units from its `unit` (a percent unit reads `Codex 3.5% of 7d`; a second Claude account reads `Claude uni 0.5% of 7d`; the fallbacks are Kiro credits and Copilot AIC). The all-time numbers are remembered like the others (merged into the store on write); Reset statistics clears them. A step that reports no usage still counts as a step, and the line says so per provider: `Kiro 2.1 credits (3 of 6 runs reported)`, or `Kiro: credits not reported` when none of that provider's runs reported (the provider is the template name before the first `-`). Totals stored before 0.21.0 have no run counts and show no such remark; a stored usage of 0 is dropped when a chat loads.
- With helpers off or not available, a `helper` step in a plan is treated as a subagent step.

### Helper models

Helper models and thinking levels are configuration in herdr-delegate (0.6.0 or later: `helpers.py config`, `set`, `custom`, `models`), and the router edits them the way it edits subagent tiers.

- **Finding helpers.py**: the path in Settings → Other subscriptions → *Set path by hand* → "Path to helpers.py" (it must end in `helpers.py`), else the newest `herdr-delegate` under `$CLAUDE_CONFIG_DIR` (default `~/.claude`)`/plugins/cache/<marketplace>/herdr-delegate/<version>/skills/herdr-delegate/scripts/`. The config is read when a chat starts, when Helpers are switched on, when the path changes and after every change. When none is found there are no helpers: the pane says helpers are optional and how to get them (see Needs), and the path can be set by hand under "Set path by hand".
- **Pickers**: Settings → Other subscriptions → Helper models lists the levels that differ from the shipped defaults; *Change…* lists each provider and each of its tiers (a router's fixed command, such as Copilot Fusion, has none) with a model picker and a thinking-level picker. The models are those the provider's CLI offered when last checked (`~/.config/herdr-delegate/models.json`; agy's ids end in the level, which is cut off here) plus the configured one; the levels are the provider's own, and for agy, whose ids carry the level, only those the model is offered at (`gpt-oss-120b`: medium). Picking a model that lacks the tier's level takes its nearest one (the higher on a tie), so `helpers.py set` is never asked for a pair it would refuse. A change runs `python3 helpers.py set <provider> <tier> model=<model> effort=<level>` (herdr-delegate checks the model against its list and the level against the provider's, and renders the template), then the config is read again. A refusal shows herdr-delegate's message under the row that asked for it (and at the top of the group) and changes nothing. A • marks a value that differs from herdr-delegate's shipped default.
- **Check models**: the button runs `helpers.py models` (it asks the installed CLIs, up to a minute for Copilot). The pane shows "checked <date>" and the lines the command printed about configured models no longer offered and newer ones in the same family ("NEWER kiro-standard: claude-sonnet-5.5 -> claude-sonnet-5.6"), so a new model is one pick away.
- **Advice** (under the cost line, with an Apply button): per provider and tier, for helper runs with no kind that ran on the model and level the tier has now, and per kind. Once there are at least 3 runs on the rung, one rung up when at least half were weak (a weak verdict or a rerun), one down when at least half were overkill and none of the last 3 was weak. The rungs are the provider's **ladder**: the models of its light, standard and deep tiers in that order (or by Kiro's credit multiplier, when `models.json` lists one for each of them), each from the lowest level the tiers give it up to high, the top model on to the provider's highest level. For Kiro with the defaults: Haiku low, medium, high, Sonnet high, Opus high, xhigh, max. Applying a tier's advice runs `helpers.py set`; applying a kind's stores a **helper choice** for that kind (provider, model, level) in the router's settings (Settings → Helpers lists them, with *reset*). A run records the provider, model and level it ran on (`hrung`); runs from before are read from the template's tier, and a tier change stamps them first so they keep the model they ran on.
- **Picks**: a helper step that has not started gets a model of its own when auto mode is on and its kind has a rung that did well (at least N runs, P% ok: the same two numbers as for subagents; the cheapest such rung of the first provider the step's tier lists), or else when its kind has a helper choice. Only a provider the step's tier lists can be picked. The router names the template: the tier's own when one already has that model and level, else a one-off made with `helpers.py custom <provider> model=.. effort=..` (once per chat and rung). The plan text and the card say `launch kiro-claude-haiku-5-5-low`; the rules tell the lead to give the picker that template first, then the tier's order (`helpers.py pick <template>,<order>`), so a provider that is out of quota falls back to the order. If the template cannot be made, the card says why and the tier order stays. The lead hears of a pick that changes after it was told as a router note. A step the lead already started keeps what it launched.


## New models

The router notices new (and gone) models by itself, has the main agent write notes on them, and shows proposed changes that you apply with one click. Nothing changes without a click.

- **What is checked, and when**: with helpers ready, each chat start reads `helpers.py models --cached --json` (herdr-delegate 0.15.0 or later; it reads `models.json` only, so it is fast) and keeps the report. When an installed provider's list is missing or older than 7 days, one `models --json` runs in the background (180 s timeout, at most once per chat; the chat does not wait), then the config and the report are read again. *Check now* in Settings → Models and *Check models* under Helper models run `models --json` too. An older helpers.py has no `--json`: nothing is read at the start, and Check models reads the command's text as before. A Claude model seen in usage for the first time is new for provider `claude`, dated today.
- **What is remembered** (store key `modelNews`, merged on write, so an older chat never overwrites newer news): `seen` (`<provider>:<model>` → the day it was first seen), `asked`, `proposals`, `dismissed`. New means first seen in the last 14 days.
- **Notes** are in `~/.config/model-router/model-notes.json` (`{ "models": { "<id>": note } }`, read at the start, written when notes arrive), over a seed the router ships (the Gemini 4 models, Gemini 3.8 Flash and the Claude models, dated 2026-11-19); the file wins for the same id. A note: name, providers, release day, a one-line summary, strengths, weaknesses, tags (`code`, `review`, `research`, `judgment`, `long-context`, `fast`, `cheap`, `careful`, `second-opinion`, `agentic`), which tier and level it fits and why, sources, the day checked and who wrote it (seed, agent or person). A note is found by exact id, else with dots and dashes treated alike (Kiro's `claude-sonnet-5.5` is Antigravity's `claude-sonnet-5-5`); the Claude aliases (`sonnet`, …) find their model's note. Settings → Models shows `Model notes (N) · checked <date>`, *Check now* and a list of every note.
- **Asking the main agent**: a new model with no note, or a configured tier's model that is no longer offered, queues ONE router note (once per model, several models in one note): when the current task is finished, offer to look the models up (release, benchmarks, strengths, weaknesses, tier and level, sources) and send the result to the plan tool.
- **The plan tool's `models` input** works on its own, like `status`: `models: { notes: [...], proposals: [{ provider, tier, model, effort, why, source? }] }`. Notes are stored by "agent", dated today; an unknown tag is dropped and named in the result, a note by the person is never overwritten. A proposal needs a provider of the helper config (or `claude`), a tier the provider has (helpers: from the config, `second` included; claude: light, standard, deep), a model the provider offers (or has configured; claude: a known model) and one of its thinking levels. Invalid items are skipped with a one-line reason each, a proposal that equals what the tier has is dropped, a dismissed one is not stored again.
- **The New models card** sits under the health line in every view, and only while a proposal is pending or a new model has no note yet. Each new model is a line (name, providers, release day, summary; `notes not written yet` until the agent writes them); each proposal reads `<tier> <provider>: <now> → <proposed> · <why>` with *Apply* and *Dismiss*. *Notes ▸* opens strengths, weaknesses, fits and sources. *Apply* runs `helpers.py set` for a helper (its refusal shows beside the button and the proposal stays) or sets the Claude tier in the settings; on success the proposal goes and the card says `applied` in place. *Dismiss* remembers the proposal.
- **Log and report**: the log gets `models-asked`, `models-check`, `models-from-agent`, `model-applied`, `model-apply-refused` and `model-dismissed`; the report and `status: true` carry each provider's list date, the new and gone models of the last 14 days, the pending proposals and the number of notes.

## Strengths and the model map

The three levels stay the simple dial. This adds finer knowledge of which model suits which kind of work, as advice you apply with a click: nothing changes routing by itself.

- **A kind's strengths** are model tags (`code`, `review`, `research`, `judgment`, `long-context`, `fast`, `cheap`, `careful`, `second-opinion`, `agentic`). Defaults: `write-code` code; `code-review` and `review` review + careful; `code-read` and `cross-check` careful + long-context; `web-research`, `research`, `literature-research` research; `design-review`, `design`, `research-assistant` judgment; `summarize` long-context + fast; `eval-run`, `sweep` agentic. A kind not in that table matches by its own words (`review` in the name: review, `research`: research, `code`: code), else it has none and nothing is suggested for it. Settings → Learning → *Strengths and model map ▸* lists the kinds (history, the rules' kinds and the plan's, at most 20, most used first): *edit* shows the ten tags as toggles, *reset* (shown once you changed a kind) goes back to the default.
- **Try** lines sit under the advice, at most 3, one per kind: `Try Gemini 4 Neon high on Antigravity for code-review (careful)` with *Apply* and *Dismiss*. A kind gets one only while it has fewer runs than auto mode needs (*N runs*, 5 by default) on the model it runs on now, and only when no learned rung or advice owns it. The candidate must carry a tag the kind wants that the kind's current model lacks (the line names those tags) and its note must fit the kind's usual tier: for Claude, the tier's own rung (so it appears when the kind has a default of its own that lacks the strength); with helpers on, each provider in the tier's order, the models its CLI offers, at the note's level when that provider has it. A kind whose runs went mostly to helpers is offered helper models, mostly to Claude agents Claude's, with no runs both. *Apply* sets the kind's default (Claude) or the kind's helper choice, the same settings the history's advice sets; *Dismiss* is remembered across chats. Only tags and fits are read; a note's weaknesses text is not parsed.
- **The model map** is under the same handle, in the same place as the tags, so each fact is shown once: under each kind, what would run its steps now: `Claude: sonnet medium (tier)`, `(kind default)` or `(auto, 6 runs)`, and with helpers on the first helper of the level's order: `Antigravity: gemini-4-neon medium (kind choice)`, `(tier)` or `(auto, 7 runs)`. Below, the models with notes, one line each: `Gemini 4 Neon · judgment, agentic, research, … · deep high, second high, standard medium`. Lines wrap on every surface; there is no grid.

## Here-step effort (experiment, off by default)

A here step runs on this chat's model, which a plan cannot change mid-chat. This experiment changes the chat's thinking level instead.

- **Turn it on**: Settings → Advanced → "Experiment: effort of steps done in this chat". The plan tool then takes `start: [<id>]`, and the rules ask the agent to call it before each here step.
- **What it does**: while a started here step runs, each request of this chat goes out at that step's tier's thinking level (light low, standard medium, deep high by default), lower or higher than the chat's own: a deep step in a chat on medium runs at high. Marking the step done returns the chat to its own level. Subagent requests are never touched.
- **Why a limit**: on most setups a change of level makes the API write the whole conversation to the prompt cache again, instead of reading it. So the router switches only while the chat is under a context limit (20k, 40k by default, 80k or 150k tokens). Over the limit the step keeps the chat's level and its card says why.
- **What it measures**: every change of level, and how many tokens the request after it wrote to the cache and read from it, remembered across chats (store key `effortLog`, last 200). Settings shows the totals. Mostly written means the switch cost a cache rewrite; mostly read means it did not. This is how to find out what a switch costs on your plan; the numbers are tokens, not your subscription's usage.
- **Limits**: the router records the level it asked for. Where the model takes effort per message, the engine may hold a change back until your next message, so a step inside one long reply may still run at the old level. Thinking already scales with the work, so the saving is unmeasured.

## Multi-day plans, links, gates and cluster jobs

For multi-day workstreams with branches, worktrees, helper terminals, reports and cluster jobs, the plan pane can persist named plans across sessions and track step artifacts and gates:

- **Artifact links** (`links` on `steps`, `start`, `done`, or incremental `update: [{id, links}]`): each step can carry `branch`, `worktree`, `helper` (Herdr terminal name, e.g. `t21`), `jobs` (Slurm/cluster job ids), `report` (report path), and `refs` (`R14`, `D22`, `PR#112`). Compact operational badges (`t21`, `job 482910 R`, `R14`) sit on line 2; full links open under `▸`.
- **Passive `<hc>` link capture**: when a Herdr helper message (`<hc from="tXX">...</hc>`) arrives and uniquely matches a step (by `links.helper` or an explicit `[stepId]`), high-precision patterns (`Submitted batch job <id>`, `report: <path>`, `branch: <name>`, `R<n>`/`D<n>`/`PR#<n>`) attach automatically without overwriting scalar links set by the lead.
- **Dependencies and approval gates**: `dependsOn: [ids]` marks a step blocked (`◌`, `waits: s1, s2`) until its dependencies finish (cycles and unknown ids warn); `gate: true | "<prompt>"` marks a step gated (`◇`) and hard-denies `Agent` delegation and `start` until the person clicks **Approve** in the pane (or the lead sets `gateApproved: true` with `approvedBy: "<short quote of the person's approval in chat>"`; `gateApproved` without `approvedBy` is refused, and chat approvals show the quote in step details and a router note).
- **Persistent named plans**: passing `name: "<slug>"` with `steps` saves the plan under `${XDG_CONFIG_HOME:-~/.config}/model-router/plans/<projectKey>/<name>.json` (`projectKey` hashes `git rev-parse --git-common-dir`, so all worktrees of a repo share plans). `plan: {action: "list" | "open" | "close" | "save", name?}` and `/router plans` manage them; a **Plans ▾** drawer sits in the pane header. A new session auto-loads when exactly one open plan exists (with a one-line note); two concurrent sessions merge step-by-step via monotonic `revision`. Unnamed plans remain ephemeral.
- **Cluster job health checks**: off by default (zero subprocesses). Configure `jobCheck` (global default) or `jobCheckByProject[projectKey]` (per-project override) in Settings (`command` with `{ids}`, e.g. `ssh cluster "squeue -h -j {ids} -o '%i %T %M %R'"`, optional `intervalSec` and `timeoutMs`). Active job ids are validated and batched into one command; **↻ Jobs** in the pane or `checkJobs: true` runs on demand, showing `R`/`PD`/`CD`/`FAIL`/`OOM`/`gone` badges (and keeping stale state with a one-line warning on failure). On a 48-column phone glance, gated steps and failing jobs surface on an alert row without scrolling.

## Log and report

- **Log** (Settings → Diagnostics → Keep a log, on by default): one JSON object per line in `${XDG_CONFIG_HOME:-~/.config}/model-router/log/YYYY-MM-DD.jsonl`, fields `t` (time) and `ev` plus the event's own: `start` (version, surface), `health` (the checks, when they change), `rules` (delivered, how), `plan` (step ids, tiers, wheres, kinds), `route` (step, model, thinking level, where the rung came from), `helper-start` (step, template, model, level, mode), `helper-done` (step, verdict, usage, minutes), `fallback` (step, reason), `verdict`, `error` (where, message: every error the router catches and carries on from). Never prompts, briefs, file contents, step titles or why-texts. Files older than 14 days are deleted when a chat starts. Writing never interrupts the router: a failure only shows in the status check.
- **Report**: *Write report* (under the health line's *Why ▸*, and in Settings → Diagnostics) or `/router report` writes `~/.config/model-router/report-YYYYMMDD-HHMM.md`: router version, platform and surface, the main chat's model, the settings that differ from the defaults, the health checks with fixes, the helper config (providers with label, CLI found, direct, this account; the mode; the orders), herdr-delegate's script path, counts (history entries, all-time steps on subagents and helpers, fallbacks, plans) and the last 100 log events. The pane then says `Report written: ~/.config/model-router/report-….md — send this file` beside the button.

## Update check

A plugin installed from a marketplace does not update by itself, so the mod looks once a day. After `session.start` it fetches the published `plugin.json` from GitHub in the background (about 5 s at most, never blocking the chat) and compares the version with its own `${plugin root}/.claude-plugin/plugin.json`; only a plain newer release counts (a pre-release or anything unreadable does not). The answer is kept per Claude account (each account updates separately). A failed check is silent (no toast, no health-line ✗) and is tried again after 6 hours; a good one after 24. It never installs anything: *Update* only fills the prompt box with a request for Claude.

- **Off**: Settings → Diagnostics → *Check for updates*, or the environment variable `CLAUDE_PLUGINS_NO_UPDATE_CHECK=1` (strict organizations). Off means nothing is requested and the pane shows no notice. A checkout or `--plugin-dir` load (anything not under the plugin cache) never checks and never offers an update.
- **`/router update`**: checks now (ignoring the back-off and both opt-outs), prints the installed and latest versions, puts the update request in the prompt box when the latest is newer, and gives the *What's new* and *How updating works* links. `/router update dismiss` stops announcing the latest version.
- **`/router help`**: at most 12 plain lines: what the router does, the three first steps, `/router`, `/router report`, `/router update`, the guide link and the installed version.
- The version shown anywhere to a person (the report, the status check, `/router update`) is read from `plugin.json`, not from a constant in the code.

## Herdr view

The pane lives inside Claude Code and cannot scroll while the plan-approval question is open, so a long plan is hard to read before approving it. If you run Claude Code in Herdr, a Herdr mod shows the plan in a normal, scrollable column on the right of the window, like the pane in the desktop app, following the chat of the focused terminal. It is **read-only**: approving, editing and settings stay in Claude Code (Herdr cannot draw Claude Code's own pane, so the view is a second, simpler drawing of the same state).

- **What it shows**, in the pane's order and words: the health line, the machine and folder of the chat it follows, `Plan · 2 of 5 done · awaiting your approval`; the New models card's lines when it has any; the steps as the pane's two-line rows, indented by depth (○ planned, ◐ running, ● done, id, the wrapping title; then the level in its colour, where it runs, model and effort, cost, verdict, kind), and a fallback; then one cost line for this plan and one for this chat. Without a state file newer than 2 days it says `No router state yet. Start a Claude Code chat with model-router 0.25 or later.`
- **How it works**: with `~/.config/herdr-app` present, each chat writes `${XDG_CONFIG_HOME:-~/.config}/model-router/state/<chat>.json` (display strings only; one write a second at most; files older than 2 days are deleted when a chat starts; the step titles are in it, so it stays on your machine). The mod reads the newest files every 2 seconds (every 10 seconds for a remote machine), from the machine of the focused Herdr space (a chat on another machine writes its file there), else from this computer, and follows the chat whose folder matches the focused terminal's. Switch the writing off in Settings → Diagnostics → *Show in Herdr* (the group's closed line says `Herdr view on` or `off`).
- **Install** (once, and again after a plugin update that changes `herdr/`; use the newest version folder):

  ```sh
  python3 ~/.claude/plugins/cache/<marketplace>/model-router/<version>/herdr/sidebar.py
  ```

  It copies the mod into `~/.config/herdr-app/mods/model-router/`, makes `main-router`, a personal copy of Herdr's `main` layout (shipped layouts are read-only), with a `router` column (380 px) on the right of the terminals, binds **⌘⇧R** to show or hide that column, and switches the window to it. Run again, it only refreshes the mod and adds what is missing. `⌘⇧L` switches back to Herdr's own layout; deleting `layouts/main-router.json` removes the copy (it does not follow later changes to Herdr's `main`; run `layout.clone` and the script again to pick them up). Without the layout, `herdr-app do pane.split '{"direction":"right","mod":"model-router"}'` opens the view beside one terminal.
- **A chat on another machine**: the column reads the state files of the machine the focused space runs on (install the plugin there; Claude Code writes the file on that machine), so a remote chat shows like a local one, refreshed every 10 seconds instead of 2.

## Keeping the rules in front of the model

- **In every chat** the mod writes the rules into the conversation as a hidden note at the start of the first turn after it loads. It also adds them to the system prompt, but some hosts (the desktop app among them) supply their own system prompt and drop added sections without a trace, so only the note counts as delivered.
- **After a summarization** of the chat, the next turn gets the rules again (where needed) and the current plan with each step's status, from the router's own record. The router keeps the id of the chat row that carried the rules and checks at each turn that the chat still holds it, so this works on Team and Enterprise accounts too, where Claude Code's built-in sec-default plugin keeps compactions (`session.compact`) and the system prompt (`prompt.compose`) from the mods a person installs; a `/clear` or a rewind past the row brings the rules back the same way. There the status line learns the model from the turn instead of the system prompt.
- **Always plan** and router notes use the same hidden note, at the start of each turn.
- **Check it**: ask the model to call the plan tool with `status: true`. It reports the version, how the rules are delivered, whether they are in the chat, counters, the helper mode, the health checks, the helpers.py status and message, the log file and the number of history entries.
- The plan, costs, history and settings live in the mod, not in the conversation, so a summary never loses them.

## The status line

Always shown under the prompt, so you can see the router is on:

- With no plan: `⇄ Router on · rules sent to opus · /router for the pane`. "Rules sent" appears once the rules are written into the chat; until then (a fresh load, or right after a summary) it says they go out with your next message.
- With a plan: progress dots, the running step and its model, subagent cost and savings.

Limits: the main chat's own model never changes; the pane suggests switching it to Sonnet when a plan has no deep step.
