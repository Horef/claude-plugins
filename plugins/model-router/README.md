# model-router

Routes each step of a multi-step task to the cheapest model tier that does it well, shows what it cost and what it saved, and learns from your reruns.

## How it works

- **Plan**: for a multi-step request the main agent first calls `mcp__model-router__plan` with steps tagged by tier (light, standard, deep) and by where they run (a subagent, or here in the main chat).
- **Parts**: a step may have `parts`, recursively (a part's id extends its parent's: `s3`, `s3.a`, `s3.a.1`), for work that splits into pieces that need different tiers or run side by side. A step with parts is a **group**: its tier only rates it, it is done when all its parts are, and its cost and usage are the sums of its parts. A part with `count: N` is N identical agents running in parallel under one id (N readers, say); it is done when the Nth run ends, and its agents' costs add up. Each part is delegated under its own id (`[s3.a.1]`); delegating the group itself is refused with the list of its parts. Naming a group in `done` marks its unfinished parts done; naming it in `start` starts them. A plan nested deeper than three levels of parts is still taken (the tool's schema spells out three). A repeated id is ignored and the agent is told.
- **Approval**: the plan waits for your answer in the chat's question dialog. Edits you make in the pane while it waits (tier, where, model, thinking) are kept whatever you pick.
  - **Run it**: go with the plan as it now stands in the pane.
  - **Run it, and auto-approve future plans**: the same, and later plans run without asking.
  - **Change the steps**: the steps themselves need work (add, drop, split or reword). Nothing runs; the model asks what to change, or, if you typed it under Other, revises right away and asks again.
- **Routing**: an Agent call whose description starts with `[<step id>]` gets its model and thinking level from the plan, whatever the main agent asked for. Forks are never rerouted, since they always inherit the parent model. The rung comes from, in order: your own picks on the step in the pane, auto mode's learned rung for the step's kind (when auto mode is on), the kind's default (set by applying advice), the tier.
- **Kinds**: each step may carry a `kind`, a short label for the kind of work (`code-review`, `summarize`, `search`, `write-code`, `figure`). The rules list the kinds the history has seen so far (taken when the chat starts, so the rules stay the same all chat), and the agent reuses them. A step routed for a mapped skill takes the skill's name as its kind. Kinds are stored as lower-case letters, digits and hyphens.
- **Verdicts**: every delegated step (subagent or helper, parts included) gets a verdict from the main agent once it has checked the result: `done: [{id, verdict, why}]`. The verdicts are defined by what happened, not by taste: **ok** = the result was used as returned or with small edits; **weak** = it needed a rerun, the agent redid part of it, or review found a substantive error; **overkill** = plainly mechanical work (finding, listing, extracting, short output, no judgment) that ran above the light tier. A subagent step is marked done when its agent ends; the agent still gives it a verdict. A delegated step marked done without one is still done, the plan tool's result asks for it in one line (once, or again when the step is named again), and the run counts as "no verdict".
- **Facts per run**, recorded without asking: kind, tier, where, the rung it ran on (model and thinking level, or the helper template), reruns, output tokens, start-up heavy, and how long it took. A finished step delegated again counts as a rerun, as does a rerun from the pane; the advice counts a rerun as weak whatever the verdict said.
- **Always plan** (Settings): every message you type carries a hidden reminder to plan before using tools.

## The pane (`/router`)

- **Cost**: a switch picks the span.
  - **This plan**: the main chat since the plan was posted, its subagents, and what they saved. A new plan (no step in common with the last) starts a new count.
  - **This chat**: since the chat was opened or its plugins reloaded; earlier turns are not counted.
  - **All time**: what delegating saved, what the subagents cost and what they would have cost on the main model, steps and plans by tier, since the first use or the last reset. Remembered across chats as a handful of numbers.
  Every view moves together: cost is counted per model response as it arrives, not when a step finishes. Saved also shows as a share of what the same work would have cost without routing (the main chat plus the subagents' tokens at the main model's prices).
  All amounts are estimates from list prices (`hooks/tiers.ts`, editable in Settings → Models) and the token counts the API reports; savings compare each step with the main chat's model doing the same tokens. Tokens on a model with no price show their cost as "?" (or "≈$0.12 + ?" when only part is unpriced) and are left out of savings.
- **Steps**: parts sit under their group, indented two cells a level (the indent stops at three levels). A group is a header with its rating, "n/m done" and the cost of its parts; every part is a card of its own with its own pickers, rerun and cost, and a `×N` tag (with the runs finished so far) when it has a count. Only the parts that do the work count as steps in the header, the status line and the Plan heading. A card per step with pickers for where (subagent, here, or helper when Helpers are on), tier, model and thinking level (buttons on mobile), its cost and tokens, and a warning when a step was mostly subagent start-up cost. A "here" step is done by this chat on its own model and thinking level, which no tier can change: its tier is a rating, shown as a label ("rated deep") that becomes a picker again when you send the step to a subagent, the default if you send it to a subagent, and a warning on the card and in the plan the agent gets back when the step is rated above this chat's model (a deep step in a Sonnet chat).
- **Edits after approval**: change a part's (or step's) where, tier, model or thinking level in the pane while the plan runs and the change goes to a draft, not to the plan: the routing and the main agent keep using the plan as it was, so a half-finished edit cannot reach the agent if a turn starts meanwhile. The edited values carry a ✎ mark, and the top of the plan shows **Send changes (N)** (N counts the changed values) and **Discard**. Send puts the draft into the plan at once (a step not yet started is routed by it from then on) and the main agent is told at its next turn, as one router note per step or part with the final values (so cycling a picker through several values sends one note, and none if you put it back); until then the card says "change noted, applies from the next turn". Discard drops the draft. A picker put back to the plan's own value leaves no edit. A plan posted anew drops an unsent draft; a rerun drops the unsent model and thinking picks of its step. Before the plan is approved (while it waits for you) edits go straight into the plan, since approval sends them. A rerun needs no note: its own message carries the new rung.
- **Rerun one rung up**: a finished step that came back weak can be redone on the next rung of the ladder (Haiku low → medium → high → Sonnet medium → high → Opus high → xhigh → Fable). The main agent is asked to delegate it again. With more models known, the ladder is built from them ordered by price: each default model keeps its rungs, a new one gets medium and high, and a model with no price is not on it.
- **Step cards** also show the step's kind, its verdict once given ("verdict weak: missed two files", or "no verdict yet"), and where its rung comes from when not from the tier ("auto: sonnet · high (learned, 5 runs)", "code-review default: sonnet · medium"). The pickers' default option says the same ("sonnet (auto)").
- **What the history says**: runs, reruns, average cost and verdicts per rung, and runs, reruns and verdicts per kind, remembered across chats. Advice per kind, and per tier for runs with no kind, once there are at least 3 runs on the rung it runs on now: one rung up when at least half were weak (a weak verdict or a rerun), one rung down when at least half were overkill and none of the last 3 was weak. Each shows its evidence ("code-review on light: 3 of 4 weak") and an Apply button: for a kind it sets the kind's default (Settings → Learning), for a tier the tier's model and thinking level. Only subagent runs move a subagent rung; helper runs have advice of their own (see Helpers, below).
- **Genome link**: when a kind's advice first reaches its threshold, the router queues one note asking the main agent to record a strange-loop observation with the note command and the evidence line (to the skill of that name if the kind is a skill, else to model-router), once per kind and direction, remembered across chats.
- **Minimal view** (header button, or Settings → Minimal view): the pane draws only what you act on: two lines per step (title, then its pickers with cost and rerun), the cost line, and tier suggestions. No cards, notices or explanatory text, so a long plan fits without scrolling. The setting is remembered across chats.
- **Settings** (opens right under its button, closes with Done, which sits at the top):
  - Always plan, auto-approve and Minimal view. Groups start with a coloured band; in Minimal view their help texts are left out too.
  - Each tier's model and thinking level. The model pickers list every known model.
  - **Learning**: *Auto mode* (off by default): a subagent step whose kind has enough history runs on the learned best rung, the cheapest rung with ok (and no rerun) in at least P% of at least N runs there, 5 runs and 90% by default (a mode that changes routing without asking wants more evidence than the advice below does); else the kind's default; else the tier's. Your own picks on a step still win. With it off, routing is as before. Under the switch, "Auto picks a rung with at least N runs and P% ok" sets the two numbers (3, 5, 8, 10 or 20 runs; 70, 80, 90, 95 or 100%), remembered and mirrored like the other settings and marked with • when they differ from the default. The advice's own thresholds (3 runs, half weak or overkill) are fixed. Below that, each kind's default (set by Apply) with a *reset*. With Helpers on, auto mode and its two numbers also pick a helper's model (see Helpers).
  - **Models**: the known models are the defaults, any model id seen in a chat's usage (ids map to family aliases, `claude-haiku-5-5` is haiku; an unknown family is kept under its id), and any added by name. Each shows its price, which you can set: "input output" in dollars per million tokens (cache write 1.25×, cache read 0.1× input) or all four; empty brings back the default (or none). Added and seen models can be removed. A new model is passed to the Agent tool by the name the router knows it by, so add it under the alias the Agent tool takes.
  - An optional scope note per tier. It adds one line to that tier's briefs: stay on the task, don't start sessions or load extra tools. Off by default.
  - Skills that should run in a subagent on a tier. A skill you've used shows up here; you can also add one by name.
  - Open pane on start: opens the pane in every new chat.
  - Reset statistics clears the all-time numbers; Clear history clears the per-run history behind the tier suggestions.
  - A small • marks every value that differs from the default, with a one-line legend, so you can see which of your own values are active.

All settings and the history are remembered across chats, in the mod's store. Settings (kind defaults, auto mode, known models and prices included), auto-approve and always-plan are also mirrored to `~/.config/model-router/settings.json` on every change: when the store is new and empty (re-adding the marketplace creates one), they come back from that file; when the store has settings, it wins and rewrites the file. History and the all-time numbers live only in the store, and nothing is written to the store until it has been read, so a response arriving while a chat loads cannot overwrite them with zeros.

**In the terminal** the pane scrolls with the keyboard: ctrl+x tab (or a click) gives it the keys, ↑↓ scroll, Esc returns to the prompt; the mouse wheel works where the terminal passes it through. A line at the top says so. The layout is compact there: the cost is one line, and while a plan awaits approval the steps come first and the cost after them.

## Helpers (other subscriptions)

Off by default; while off, nothing helper-related in the rules, the plan tool or the pane changes. When on, a plan step can run in a third place, **helper**: an agent on another subscription (Kiro, Copilot, agy) that the main chat starts through a delegation skill.

- **Needs**: the delegation skill (default `herdr-delegate`; the name is a stored setting under `helpers`; each tier's helper order is edited in the pane), herdr-core `hc`, and at least one helper CLI. The mod runs no shell commands of its own while Helpers are off. While they are on it runs herdr-delegate's `helpers.py` (python3, no shell) to read and change helper models; it never checks that `hc` or a CLI exists, it only shapes the plan and the rules. Without `helpers.py` everything below that needs it falls back to the tier orders and the pane shows the command to run by hand.
- **Turn it on**: Settings → Helpers → "Helpers (other subscriptions)". The plan tool offers `helper` from then on: switching registers the tool again, which replaces its schema at once (and costs the chat one prompt-cache refresh).
- **Use for** (Settings): *long steps* sends only long self-contained steps (research, code to a spec, sweeps, over ~15 tool calls) to helpers and leaves shorter ones to subagents; *all steps* sends every self-contained step that would otherwise be a subagent step.
- **Order**: each tier lists the helpers to try, e.g. deep: `kiro-deep → copilot-deep → agy-deep`. The plan and the step cards show it. Settings → Helpers lists each tier's helpers in order with ↑ / ↓ to move one and *off* to drop it (dropped helpers come back with *+ name*), and *Reset to default order*. The order is stored as the comma string under `helpers.tiers.<tier>`. A changed order reaches a chat that already has the rules as one router note (none if it is back to what the chat was told).
- **Copilot Fusion** (Settings, off by default): *Max for deep* adds `copilot-fusion-max` to the deep order; *High + Max* also adds `copilot-fusion-high` to standard. Each goes just before the pinned Copilot helper, since both use Copilot's quota. Fusion is GitHub's router across Claude and GPT-6 models, not a fixed model. Fusion Max scored close to Claude Code with Opus 5.5 at max effort for about half the cost; High has not been measured (herdr-delegate's SKILL.md has the details). Changing it mid-chat sends the new orders to the chat as a router note.
- **Without helpers**: when none is usable (no `hc`, no CLI, nothing the picker finds), the main chat runs the step as a normal subagent and says so. A helper step run that way becomes a subagent step, routed and costed like any other.
- Helper steps have no Claude subagent usage, so they show no cost and are not counted in the subagent totals. The main chat marks them done itself.
- **Which helper, which model**: when the main chat starts a helper step it calls the plan tool with `start: [{id, helper: "copilot-standard", model: "Claude Sonnet 5.5"}]` (plain ids still work): the template it launched and the model the helper reports on its own screen. The card shows "copilot-standard · Claude Sonnet 5.5 · high": the last part is the helper's thinking level. It is the `effort` the main chat reports in the same `start` object when the helper's screen shows one; else the router reads it from the helper's template, `~/.config/herdr-core/templates/<template>.md` (its `command:` line: Kiro `--effort X`, Copilot `--reasoning-effort X`, agy the level its model id ends with, e.g. `gemini-4-argon-high`); a template that sets none (Copilot Fusion chooses per step) shows no level. A later `start` that names only a model keeps the level. The router does not check the model against the template's name; it shows what was reported. On a part's card in the minimal view the same line shows for a helper part, and a subagent part shows its model and thinking pickers.
- **Helper usage**: when it marks the step done the main chat passes its verdict and the usage line the helper's screen ends with: `done: [{id, verdict, why, usage: {provider: "copilot", amount: 30.04, unit: "AIC"}}]` (Copilot: "Session: N AIC used"; Kiro: its credits line, unit "credits"). It is recorded once per step; the card shows it with how long the step ran (from start to done), and nothing is converted to money. Plain ids still work.
- **What moved off Claude**: the cost card (plan, chat and all-time views) adds a line such as `Moved off Claude: 4 helper steps, 38 min; Copilot 30.04 AIC; Kiro 2.1 credits`: finished helper steps, their running time, and the usage added up per provider and unit. The all-time numbers are remembered like the others (merged into the store on write); Reset statistics clears them. A step that reports no usage still counts as a step.
- With helpers off, a `helper` step in a plan is treated as a subagent step.

### Helper models

Helper models and thinking levels are configuration in herdr-delegate (0.6.0 or later: `helpers.py config`, `set`, `custom`, `models`), and the router edits them the way it edits subagent tiers.

- **Finding helpers.py**: the path in Settings → Helpers → "Path to helpers.py" (it must end in `helpers.py`), else the newest `herdr-delegate` under `~/.claude/plugins/cache/<marketplace>/herdr-delegate/<version>/skills/herdr-delegate/scripts/`. The config is read when a chat starts, when Helpers are switched on, when the path changes and after every change. When none is found the pane says so and shows the command to run by hand (`helpers.py set <provider> <tier> model=<model> effort=<effort>`); nothing else changes.
- **Pickers**: Settings → Helpers → Helper models lists each provider and each of its tiers (a router's fixed command, such as Copilot Fusion, has none) with a model picker and a thinking-level picker. The models are those the provider's CLI offered when last checked (`~/.config/herdr-delegate/models.json`; agy's ids end in the level, which is cut off here) plus the configured one; the levels are the provider's own. A change runs `python3 helpers.py set <provider> <tier> model=<model> effort=<level>` (herdr-delegate checks the model against its list and the level against the provider's, and renders the template), then the config is read again. A refusal shows herdr-delegate's message in the pane and changes nothing. A • marks a value that differs from herdr-delegate's shipped default.
- **Check models**: the button runs `helpers.py models` (it asks the installed CLIs, up to a minute for Copilot). The pane shows "models checked <date>" and the lines the command printed about configured models no longer offered and newer ones in the same family ("NEWER kiro-standard: claude-sonnet-5.5 -> claude-sonnet-5.6"), so a new model is one pick away.
- **Advice** (under "What the history says", with an Apply button): per provider and tier, for helper runs with no kind that ran on the model and level the tier has now, and per kind. Once there are at least 3 runs on the rung, one rung up when at least half were weak (a weak verdict or a rerun), one down when at least half were overkill and none of the last 3 was weak. The rungs are the provider's **ladder**: the models of its light, standard and deep tiers in that order (or by Kiro's credit multiplier, when `models.json` lists one for each of them), each from the lowest level the tiers give it up to high, the top model on to the provider's highest level. For Kiro with the defaults: Haiku low, medium, high, Sonnet high, Opus high, xhigh, max. Applying a tier's advice runs `helpers.py set`; applying a kind's stores a **helper choice** for that kind (provider, model, level) in the router's settings (Settings → Helpers lists them, with *reset*). A run records the provider, model and level it ran on (`hrung`); runs from before are read from the template's tier, and a tier change stamps them first so they keep the model they ran on.
- **Picks**: a helper step that has not started gets a model of its own when auto mode is on and its kind has a rung that did well (at least N runs, P% ok: the same two numbers as for subagents; the cheapest such rung of the first provider the step's tier lists), or else when its kind has a helper choice. Only a provider the step's tier lists can be picked. The router names the template: the tier's own when one already has that model and level, else a one-off made with `helpers.py custom <provider> model=.. effort=..` (once per chat and rung). The plan text and the card say `launch kiro-claude-haiku-5-5-low`; the rules tell the lead to give the picker that template first, then the tier's order (`helpers.py pick <template>,<order>`), so a provider that is out of quota falls back to the order. If the template cannot be made, the card says why and the tier order stays. The lead hears of a pick that changes after it was told as a router note. A step the lead already started keeps what it launched.


## Here-step effort (experiment, off by default)

A here step runs on this chat's model, which a plan cannot change mid-chat. This experiment changes the chat's thinking level instead.

- **Turn it on**: Settings → Experiment → "Adjust effort of here steps". The plan tool then takes `start: [<id>]`, and the rules ask the agent to call it before each here step.
- **What it does**: while a started here step runs, each request of this chat goes out at that step's tier's thinking level (light low, standard medium, deep high by default), lower or higher than the chat's own: a deep step in a chat on medium runs at high. Marking the step done returns the chat to its own level. Subagent requests are never touched.
- **Why a limit**: on most setups a change of level makes the API write the whole conversation to the prompt cache again, instead of reading it. So the router switches only while the chat is under a context limit (20k, 40k by default, 80k or 150k tokens). Over the limit the step keeps the chat's level and its card says why.
- **What it measures**: every change of level, and how many tokens the request after it wrote to the cache and read from it, remembered across chats (store key `effortLog`, last 200). Settings shows the totals. Mostly written means the switch cost a cache rewrite; mostly read means it did not. This is how to find out what a switch costs on your plan; the numbers are tokens, not your subscription's usage.
- **Limits**: the router records the level it asked for. Where the model takes effort per message, the engine may hold a change back until your next message, so a step inside one long reply may still run at the old level. Thinking already scales with the work, so the saving is unmeasured.

## Keeping the rules in front of the model

- **In every chat** the mod writes the rules into the conversation as a hidden note at the start of the first turn after it loads. It also adds them to the system prompt, but some hosts (the desktop app among them) supply their own system prompt and drop added sections without a trace, so only the note counts as delivered.
- **After a summarization** of the chat, the next turn gets the rules again (where needed) and the current plan with each step's status, from the router's own record.
- **Always plan** and router notes use the same hidden note, at the start of each turn.
- **Check it**: ask the model to call the plan tool with `status: true`. It reports the version, how the rules are delivered, whether they are in the chat, and counters.
- The plan, costs, history and settings live in the mod, not in the conversation, so a summary never loses them.

## The status line

Always shown under the prompt, so you can see the router is on:

- With no plan: `⇄ Router on · rules sent to opus · /router for the pane`. "Rules sent" appears once the rules are written into the chat; until then (a fresh load, or right after a summary) it says they go out with your next message.
- With a plan: progress dots, the running step and its model, subagent cost and savings.

Limits: the main chat's own model never changes; the pane suggests switching it to Sonnet when a plan has no deep step.

## Install

```
/plugin install model-router --marketplace Horef/claude-plugins
```

Chats that were already open load it after `/reload-plugins`, typed in that chat; new chats load it by themselves.
